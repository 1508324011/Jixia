# Jixia 产品设计文档（目标态）

> 用途：用于产品与工程团队内部对齐 Jixia 的目标态产品定义、信息架构与关键设计原则。  
> 状态：当前版本为目标态产品设计基线，不等同于已全部实现的功能清单。

## 1. 产品定义

Jixia 是一个面向科研实验室团队的**一体化研究操作系统**。

它服务的不是单点工具需求，而是实验室日常研究工作中一整条连续链路：外部文献发现、个人资料沉淀、深度阅读、思考与综合、项目内共享知识构建，以及 AI 辅助下的持续研究推进。

Jixia 的目标，不是把科研活动拆成彼此割裂的“搜索工具、阅读工具、笔记工具、写作文档、聊天工具”，而是把这些行为组织为一套连贯、可回到上下文、可逐步沉淀的研究工作环境。

Jixia 的核心产品判断包括：

- **Home 是日常驾驶舱**：承载用户每天进入系统后的优先事项、最近进展、待继续事项与项目入口。
- **Project 是首要工作单元**：科研协作、共享知识、正式文稿和团队可见的研究进展，都围绕 Project 组织。
- **Project Overview 只是资源入口页，不是项目主驾驶舱**：它承担导览、入口与概览职责，而不是承载所有项目日常操作。
- **Library 是个人文献资产仓库**：它首先是研究者自己的文献库存与管理中心，而不是公共资料池首页。
- **Search 只负责外部发现**：它面向外部数据库、DOI、URL、论文来源的发现与引入；系统内部对象检索应由独立的全局搜索 / 命令入口承担。
- **Reader 专注深读**：阅读、标注、摘录与引用定位应在 Reader 内完成，而不是在这里承载所有综合思考和协作写作。
- **Notebook 是个人思考与综合空间**：它服务个人判断、假设、问题拆解、跨文献对比与研究草稿，不是共享项目文档。
- **Project Docs 是结构化共享知识中心**：它承载团队内正式、可持续维护、可追溯的项目知识与文稿。
- **AI 以嵌入式 copilot 为主**：AI 应分布在各个工作面中辅助研究者，而不是成为产品唯一入口；AI Workspace 保留为顶层模块，但属于次级工作面，用于复杂、长上下文任务。

Jixia 的根本哲学是：**支持研究判断，而不是用流水线替代研究判断。**

系统应该帮助研究者形成理解、组织证据、建立上下文、沉淀知识，而不是试图把科研过程机械化地压缩成“导入—分析—生成—完成”的自动管线。

## 2. 目标用户与使用场景

### 2.1 核心用户

Jixia 的主要用户包括：

- **PI / 课题组负责人（Lab Lead）**
- **博士后（Postdoc）**
- **研究生（Graduate Student）**
- **科研助理（Research Assistant）**
- **实验技术员（Lab Technician）**

这些角色共同构成实验室的研究协作链，但他们在系统中的关注重点不同。

### 2.2 典型使用诉求

#### PI / 课题组负责人

- 快速了解各项目当前进展与风险点
- 查看项目内已经沉淀的共享知识、关键证据与文稿状态
- 基于项目上下文审阅团队结论，而不是逐条翻找私人笔记
- 在需要时使用 AI Workspace 处理较复杂的综述、方案比较或提纲梳理任务

#### 博士后

- 高频进行文献搜索、筛选、精读与综合
- 将个人研究判断逐步沉淀为可复用的知识结构
- 在多个项目间承担桥接角色，把成熟认识带入项目共享文档
- 借助 AI 做总结、改写、提纲建议与问题追问，但保留最终判断权

#### 研究生

- 围绕具体课题持续进行 Search → Library → Reader → Notebook 的个人研究闭环
- 在 Notebook 中整理问题、记录假设、积累摘录与引用
- 当研究趋于稳定时，进入 Project Docs 参与团队共享知识构建

#### 科研助理 / 实验技术员

- 负责特定主题下的资料搜集、整理与引用准备
- 维护项目相关资料的完整性与可追溯性
- 在有限权限下协助项目文档的结构化更新

### 2.3 典型使用场景

Jixia 重点服务以下高频场景：

1. **日常研究推进**：研究者每天从 Home 进入，继续昨天未完成的阅读、笔记与项目工作。
2. **专题文献探索**：用户在 Search 中做外部发现，将值得持续跟进的材料纳入个人 Library。
3. **深度阅读与证据抽取**：用户在 Reader 中阅读论文、做标注、摘录关键段落、整理引用线索。
4. **个人综合与判断形成**：用户在 Notebook 中围绕研究问题做跨论文对比、形成观点、整理草稿。
5. **项目知识沉淀与协作**：团队在 Project Docs 中维护共享背景、研究假设、设计 rationale、结论与正式文稿。
6. **长上下文 AI 辅助任务**：用户在 AI Workspace 中处理需要较长上下文、跨资料聚合或反复追问的复杂任务。

## 3. 产品边界与不做什么

为了保持产品内核清晰，Jixia 明确有边界。

### 3.1 Jixia 不是以下产品

- **不是完整 ELN（Electronic Lab Notebook）/ LIMS 系统**
- **不是实验执行管理系统**
- **不是样本、仪器、试剂、流程排班的综合运营系统**
- **不是独立的团队聊天软件**
- **不是通用项目管理软件**
- **不是自动替代研究判断的科研流水线引擎**

Jixia 关注的是**研究认知工作**，而不是实验执行调度、实验室资产运营或组织管理全栈。

### 3.2 明确不做什么

1. **不设计独立任务管理模块**  
   用户可以在 Notebook 或 Project Docs 中书写计划、待办、研究步骤，但系统不引入单独的 task board / sprint / gantt 模块。

2. **不把 Discussion 设计成独立聊天中心**  
   Discussion 以对象附着为主，围绕具体文档、具体摘录、具体项目对象发生，而不是做成一个脱离对象上下文的 standalone chat 模块。

3. **不把 Search 设计为系统内一切检索的总入口**  
   Search 只负责外部发现。内部对象的定位、跳转与调用，应通过独立的全局搜索 / 命令入口来完成。

4. **不设计显式的跨模块“投递 / 推送 / 输送”机制**  
   系统支持引用、参考、重新组织与人工重述，但不把产品主链设计成显式的“从 A 推到 B”“从 Notebook 一键送入 Project Docs”之类的跨模块投递机制。

5. **不让 AI 默认代表用户做持久化决策**  
   AI 可以建议、起草、总结、改写，但不会在未经用户确认的情况下默认写入 Notebook、Project Docs 或其他正式对象。

6. **不把 Space 做成强前台工作空间**  
   Space 是治理容器，不是主要用户认知中的日常工作空间。用户的核心前台心智应围绕个人工作与 Project 展开。

## 4. 核心设计原则

### 4.1 支持研究判断，而非替代研究判断

Jixia 必须围绕研究者的判断过程设计，而不是围绕自动化流水线设计。系统应帮助用户建立理解、组织材料、回看证据、形成观点，并保留不确定性、中间态与反复修正的空间。

### 4.2 项目优先，但个人先行

Project 是团队协作的首要工作单元，但研究工作的真实起点通常发生在个人层面。因此，系统必须同时支持：

- 个人先进行探索、阅读、记录与综合
- 在成熟后进入项目上下文，形成共享知识

这决定了 Jixia 不是“先建项目再做一切”，而是“个人循环与项目循环并存，但项目是正式协作归属”。

### 4.3 工作面职责必须清晰

每个核心模块必须有明确职责：

- Home：日常驾驶舱
- Search：外部发现
- Library：个人资产沉淀
- Reader：深读与摘录
- Notebook：个人综合与判断形成
- Project Docs：结构化共享知识
- AI Workspace：复杂长上下文任务

避免一个工作面承载所有能力，导致每个模块都变弱。

### 4.4 默认归个人，显式进入项目

除明确创建于项目内的对象外，新资产默认先归个人所有。进入项目共享语义必须是明确的、范围受控的、以项目为边界的，而不是隐式扩散。

### 4.5 严格的项目范围共享

共享不应是模糊的“组内可见”，而应是严格的 **project-scoped sharing**。用户是在某个 Project 中协作，而不是在一个泛化的大空间里无边界共享。

### 4.6 AI 是协作者，不是替代者

AI 的价值在于辅助理解、压缩信息、提出结构建议、协助草拟、回答问题，而不是在后台代替研究者生成最终结论。Jixia 的 AI 设计必须始终把用户保持在决策闭环中。

### 4.7 编辑体验应连续、一致、可迁移

Notebook 与 Project Docs 虽然归属不同，但编辑器体验必须高度统一，形成连续的认知与操作语法。用户不应在“私人写作”和“共享写作”之间切换完全不同的编辑模型。

### 4.8 治理存在，但不喧宾夺主

Space、权限、范围、审计等治理结构必须真实存在，但应尽量弱化其前台存在感，让用户的工作心智保持在研究问题、文献、笔记与项目之上。

## 5. 核心对象模型

Jixia 的目标态产品需要围绕一组清晰的核心对象展开。

| 对象 | 定义 | 默认归属 | 共享方式 | 说明 |
| --- | --- | --- | --- | --- |
| 用户（User） | 系统中的个人研究者 | 个人 | 可参与多个项目 | 一切个人工作与权限判断的基础 |
| Space | 实验室/组织级治理容器 | 组织 | 通过治理生效 | 前台弱可见，不作为主要工作面 |
| Project | 团队协作的首要工作单元 | 项目 | 项目成员可见 | 围绕研究目标组织共享知识与协作 |
| 外部发现结果（External Discovery Result） | 来自数据库、DOI、URL 等的外部候选 | 个人操作上下文 | 不直接共享 | Search 只处理这类外部发现对象 |
| Library Asset | 进入个人文献库的文献资产 | 默认个人 | 可在明确项目范围内引用或纳入项目上下文 | Library 首先是个人仓库 |
| Reader Annotation / Excerpt | 阅读过程中产生的标注与摘录 | 默认个人 | 按对象与范围控制 | 用于支持阅读理解与引用定位 |
| Notebook Document | 个人思考与综合文档 | 个人 | 默认不共享 | 围绕研究问题组织，不是共享文稿 |
| Project Doc | 项目内共享文档 | 项目 | 项目成员共享 | 承载项目知识、正式草稿与结构化沉淀 |
| Citation / Reference | 引用与参考信息 | 随所附着对象存在 | 可随项目对象共享 | 系统支持引用，不等于设计跨模块投递 |
| AI Session / AI Workspace | AI 交互上下文 | 默认个人 | 可在项目上下文中使用，但不自动转成项目资产 | 用于复杂问答、长上下文整理与起草辅助 |
| Object-attached Discussion | 附着于对象的讨论 | 随对象范围而定 | 随对象共享范围可见 | 不是独立聊天模块 |

### 5.1 对象关系的基本判断

- **Project 是共享知识的正式归属单元**。
- **Notebook 是个人思考单元**，不与 Project Docs 合并。
- **Library Asset 是个人研究库存的核心资产**。
- **Citation / Reference 是跨工作面一致支持的基础能力**，但不意味着存在显式“跨模块输送机制”。
- **AI Session 不是正式知识对象本身**，其价值在于辅助用户产出，而不是替代正式对象。

### 5.2 关于 Project Overview

Project Overview 不是一个独立对象真相层，而是一个**项目资源入口页**。它的职责是帮助用户进入项目相关资源，而不是承担项目全部日常协作行为。

## 6. 信息架构

Jixia 的目标态信息架构如下：

```text
顶层导航
├── Home
├── Projects
├── Search
├── Library
├── Notebook
├── AI Workspace
└── 全局搜索 / 命令入口（跨系统辅助入口，不等同于 Search）

项目内层级
└── Project
    ├── Project Overview
    ├── Project Docs
    ├── Project Resources / Related Assets
    └── Project-level discussions / activity / members
```

### 6.1 顶层模块说明

- **Home**：日常驾驶舱，优先级最高的日常入口
- **Projects**：项目列表与进入项目的主要入口
- **Search**：外部发现入口，仅处理外部资源发现
- **Library**：个人文献资产仓库
- **Notebook**：个人思考与综合空间
- **AI Workspace**：复杂、长上下文任务的专用工作面，保留为顶层但不是日常第一入口

### 6.2 辅助入口

- **Global Search / Command**：独立于 Search，用于内部对象的全局定位、快速跳转与命令式操作

这一区分非常关键：

- Search = 面向外部世界的发现
- Global Search / Command = 面向系统内部对象的检索与调用

### 6.3 项目内信息架构判断

Project 内部不应被设计成另一个“独立产品壳层”，而应保持简单清晰：

- **Project Overview**：资源入口与概览页
- **Project Docs**：共享知识主阵地
- 其他项目相关资源与成员、活动、讨论作为补充视图存在

项目内真正长期工作的主要落点，应是 **Project Docs**，而不是 Project Overview。

### 6.4 Space 的可见性

Space 作为实验室级治理容器，主要出现在：

- 权限与成员治理
- 项目归属
- 系统设置
- 审计与边界控制

它不应在前台被塑造成用户每天进入和停留的主工作面。

## 7. 核心模块设计

### 7.1 Home：日常驾驶舱

Home 是用户每天进入 Jixia 后的第一工作面。

它的职责不是展示静态欢迎信息，而是帮助用户立即恢复研究上下文与当天工作。

Home 应重点回答：

- 我今天最应该继续什么？
- 最近哪些文献还没读完？
- 哪些 Notebook 正在推进？
- 哪些项目最近有更新？
- 哪些 AI 任务或长上下文问题值得继续？

Home 的核心特征：

- 强调“继续工作”而不是“浏览功能”
- 面向个人日常节奏
- 连接个人循环与项目循环

### 7.2 Projects：项目是首要工作单元

Projects 是团队协作视角下最重要的组织入口。

Project 的定义不是“文件夹”，而是围绕共同研究目标建立的正式协作上下文。它承载：

- 团队共享的研究目标
- 结构化共享知识
- 项目范围内的正式文档
- 项目成员的协作边界

### 7.3 Project Overview：资源入口页，不是项目主驾驶舱

Project Overview 应承担以下职责：

- 概览项目目标、状态与最近活动
- 提供进入 Project Docs、相关资源、成员与上下文信息的入口
- 帮助新进入项目的成员快速理解“这个项目里有什么”

它**不是**：

- 所有项目工作的主操作界面
- 项目级“今日页”
- 替代 Project Docs 的项目主中心

### 7.4 Search：仅负责外部发现

Search 的目标非常明确：

- 查询外部论文与相关资料
- 对外部结果进行筛选与判断
- 支持 DOI、题名、来源等外部发现方式

Search 不负责：

- 系统内部对象检索
- 个人知识回顾
- 项目知识导航

因此，Search 不是“系统万能搜索框”，而是**外部 discovery workbench**。

### 7.5 Library：个人文献资产仓库

Library 是 Jixia 中个人研究资产的核心沉淀处。

它首先回答的是：

- 我已经纳入自己工作体系的文献有哪些？
- 哪些值得继续读？
- 哪些已经读过、标过、用过？
- 哪些与我的研究问题或项目有关？

Library 的设计判断：

- 默认是**个人资产仓库**
- 可以按状态、主题、标签、近期使用等方式组织
- 应支持从个人视角出发，再在项目范围内理解相关性

它不是一个被动收藏夹，而是个人研究库存的组织中心。

### 7.6 Reader：阅读、标注、摘录与引用定位

Reader 是单篇材料的深度阅读工作面。

Reader 的职责包括：

- 阅读全文
- 做标注
- 捕获摘录
- 定位引用来源
- 支持围绕当前材料进行局部理解

Reader 的边界同样明确：

- 不承担跨多篇材料的主要综合思考
- 不承担项目正式文稿主编辑
- 不承担一个完整聊天系统的角色

Reader 的核心价值在于让研究者真正“读进去”，并把重要内容变成后续可引用、可回看、可思考的素材。

### 7.7 Notebook：个人思考与综合空间

Notebook 是个人研究判断形成的核心空间。

它服务于：

- 问题拆解
- 假设记录
- 跨论文对比
- 观点组织
- 草稿片段整理
- 私人研究路线思考

Notebook 的关键判断：

- 它是**个人空间**，而不是共享文档区
- 它以**研究问题与思考主题**组织，而不是以项目树或单篇论文组织
- 它允许中间态、试错、未定稿和反复改写

Notebook 是研究者“把看到的东西变成自己的理解”的地方。

### 7.8 Project Docs：结构化共享知识中心

Project Docs 是项目内共享知识与正式文稿的中心。

它承载的不是临时聊天内容，而是团队可以持续维护、回溯和扩展的结构化知识，如：

- 项目背景与研究问题
- 关键文献综述
- 方法方案讨论结果
- 证据与引用组织
- 实验或研究设计 rationale
- 共享结论与正式草稿

Project Docs 是项目内真正的知识中枢。

### 7.9 AI capabilities：嵌入式 copilot 为主

AI 在 Jixia 中不是单点模块，而是广泛分布在各个工作面中：

- 在 Search 中帮助结果理解与筛选建议
- 在 Reader 中帮助解释、总结、提问与定位重点
- 在 Notebook 中帮助重写、提纲建议、总结和问题回答
- 在 Project Docs 中帮助结构建议、草拟与表述优化

AI 的主形态应是**嵌入式 copilot**，始终服务当前工作面。

### 7.10 AI Workspace：顶层保留，但为次级工作面

AI Workspace 仍然保留为顶层模块，但其定位是：

- 处理复杂、长上下文、多轮追问任务
- 容纳需要聚合多个对象、多个来源、多个阶段思考的 AI 工作
- 作为用户主动进入的高级辅助空间

它不是整个产品的第一主入口，也不替代其他工作面的嵌入式 AI。

### 7.11 Discussion：弱化、附着于对象

Discussion 在 Jixia 中应保持弱化。

它的设计原则是：

- 尽量附着在具体对象上发生，例如某段文档、某条摘录、某篇材料、某个项目对象
- 强调上下文
- 服务协作澄清与判断对齐

它不应发展成脱离对象上下文的独立聊天主场。

## 8. 核心工作流设计

Jixia 的核心工作流由两个互相衔接的环路构成：**个人研究环** 与 **项目协作环**。

### 8.1 个人研究环

Jixia 的个人研究主循环是：

`Search → Library → Reader → Notebook`

其含义是：

1. 用户先在 **Search** 中做外部发现
2. 值得持续关注的内容进入 **Library**，成为个人研究资产
3. 用户在 **Reader** 中进行深读、标注、摘录与引用定位
4. 用户在 **Notebook** 中围绕研究问题形成理解、比较材料、组织判断

这一循环体现的不是线性流水线，而是个人研究判断逐步成熟的过程。用户可以在这个环路中反复往返、回看、修正、补充，而不被强制推进到下一个阶段。

### 8.2 项目协作环

当个人理解趋于成熟后，团队协作围绕 Project 展开。

项目协作环的核心判断是：

- **Project 是正式共享工作单元**
- **Project Docs 是共享知识中心**
- **成熟的个人输出会影响项目知识**，但这种影响应以用户有意识的重述、引用、重组和正式写入为基础，而不是依赖跨模块自动投递

也就是说，个人研究和项目知识之间存在连续关系，但不通过显式“推送链路”来表达。

### 8.3 典型协作路径

一个典型团队协作过程可能是：

1. 研究者在个人环中完成一轮文献发现、阅读与综合
2. 研究者进入某个 Project，查看该项目的目标、上下文与现有共享知识
3. 在 **Project Docs** 中，研究者基于自己的判断与文献依据，补充正式的共享内容
4. 其他成员在项目内查看、讨论、修订和继续扩展

这里的关键不是“把个人内容送进项目”，而是**让成熟判断进入共享知识**。

### 8.4 Home 在工作流中的位置

Home 不属于某一条线性流程中的一步，而是整个系统的日常调度层。

它帮助用户：

- 找到下一个最值得继续的事项
- 从个人循环回到项目循环
- 从项目循环回到个人探索

因此，Home 更像驾驶舱，而不是流程站点。

## 9. 权限、归属与协作机制

### 9.1 默认归属原则

Jixia 采用**个人优先的默认归属原则**。

除非对象是在明确项目上下文中创建并定义为项目对象，否则新资产默认先归个人。

这意味着：

- 新纳入的文献资产默认先进入个人 Library
- 新产生的个人思考默认属于 Notebook
- 个人研究过程中的中间状态默认不自动变成团队共享对象

### 9.2 项目共享原则

项目共享必须满足两个要求：

1. **显式进入项目上下文**
2. **共享范围严格限定在项目内**

Jixia 不应提供一种模糊的“实验室所有人默认都能看到”的共享逻辑。共享必须围绕具体 Project 建立。

### 9.3 Notebook 与 Project Docs 的归属边界

- **Notebook 属于个人**
- **Project Docs 属于项目**

两者可以共享编辑语法，但不能共享归属语义。

这是产品边界中的关键一条：

- Notebook 不是半共享草稿
- Project Docs 不是个人笔记自动升级版

### 9.4 Discussion 的协作原则

讨论以对象附着为主，协作应尽量围绕：

- 某段项目文档
- 某条引用
- 某个摘录
- 某个具体项目对象

这样可以保持协作过程可追踪、可回看，也避免讨论与知识对象脱节。

### 9.5 Space 的治理角色

Space 负责：

- 组织级成员与权限治理
- 项目所属边界
- 更高层级的可见性控制

但在用户前台心智中，Space 应尽量弱化。用户真正工作的地方是 Home、个人模块与 Project。

## 10. AI 设计原则

### 10.1 AI 以嵌入式辅助为主

Jixia 的 AI 首先应该分布在各个工作面中，围绕当前任务提供即时帮助，而不是要求用户总是跳到一个单独的 AI 页面才能获得支持。

### 10.2 AI Workspace 用于复杂与长上下文任务

尽管 AI 主要以嵌入式 copilot 存在，但仍保留 **AI Workspace** 作为顶层模块，以承载：

- 长上下文整理
- 多轮复杂追问
- 跨材料比较
- 复杂起草任务
- 需要持续会话记忆的研究辅助

它是重要模块，但不是产品中心。

### 10.3 AI 只能建议，不能默认持久化

在 Notebook 与 Project Docs 中，AI 的能力应以**建议导向**为原则。它可以：

- 总结
- 改写
- 提建议结构
- 草拟内容
- 回答问题

但它**不能在未经用户确认时默认把修改持久化写入正式内容**。

### 10.4 AI 应增强判断，而不是掩盖判断

AI 的目标是帮助研究者更快理解、更好组织、更清楚表达，而不是让用户失去对研究逻辑、引用依据与结论边界的控制。

Jixia 必须避免把 AI 设计成“替你完成研究”的黑箱。

### 10.5 AI 输出应尽量与上下文和引用保持关联

当 AI 参与总结、解释与起草时，应尽可能帮助用户保留：

- 来源意识
- 引用意识
- 上下文关系

这样 AI 才是研究工作的一部分，而不是脱离材料的语言生成器。

## 11. 编辑器设计原则（Notion-like）

Jixia 的编辑器策略应明确为：**强 Notion-like**。

### 11.1 Notebook 与 Project Docs 共享同一核心编辑语法

Notebook 和 Project Docs 虽然归属不同，但必须共享相同或高度一致的核心编辑能力，包括但不限于：

- 标题层级
- 段落与富文本
- 列表
- 引用块
- Callout / Highlight
- 表格
- 折叠结构
- 嵌入引用与参考信息
- 可组织的块级内容

这能让用户在私人思考与正式协作之间保持连续的写作体验。

### 11.2 编辑器首先服务知识组织，而不是服务表单填写

Notebook 与 Project Docs 都不应该退化成：

- 问题问卷
- 线性 textarea
- 固定表单式输入器

它们应该让用户能够像在现代知识文档系统中一样，逐步搭建自己的结构。

### 11.3 同一语法，不同语义

虽然两类文档共享编辑器语法，但语义不同：

- **Notebook**：私人、开放、中间态、允许试错
- **Project Docs**：共享、正式、结构化、面向长期维护

编辑器统一，不代表归属与权限统一。

### 11.4 计划与待办写在文档里，而不是另开模块

Jixia 不单独设计任务管理模块。用户如果需要规划行动，可以在：

- Notebook 中写个人研究计划与 TODO
- Project Docs 中写项目计划、分工说明与后续事项

这意味着编辑器需要自然支持轻量计划表达，但产品不发展为独立 task system。

### 11.5 AI 在编辑器中必须保持“建议模式”

AI 对编辑器内容的介入方式必须以建议为主，例如：

- 给出改写建议
- 推荐结构
- 生成草稿候选
- 对选中段落进行总结或扩展

所有实际写入都应经过用户确认。

## 12. MVP 与演进方向

### 12.1 MVP 应明确交付什么

Jixia 的 MVP 应优先验证以下目标态骨架：

1. **清晰的顶层信息架构**  
   至少包括 Home、Projects、Search、Library、Notebook、AI Workspace，以及项目内的 Project Overview 与 Project Docs。

2. **Search / Library / Reader / Notebook 的个人研究闭环**  
   让用户能够完成外部发现、个人文献沉淀、深读与个人综合。

3. **Project 作为主要协作单元**  
   让项目成为共享知识和正式文稿的真实归属地。

4. **Project Docs 作为共享知识中心**  
   支持结构化项目文档，而不是停留在简单文本编辑。

5. **嵌入式 AI + AI Workspace 的双层 AI 结构**  
   既支持当前上下文辅助，也支持复杂长上下文任务。

6. **Notebook / Project Docs 的统一编辑器基础**  
   至少建立共享编辑语法与一致的文档体验方向。

7. **严格的默认归属与项目范围共享逻辑**  
   确保产品边界从一开始就是诚实的。

### 12.2 MVP 不必一次做满的能力

以下能力可以作为后续演进方向，而不是 MVP 的阻塞项：

- 更强的全局搜索 / 命令系统
- 更成熟的对象附着讨论体验
- 更完整的引用管理、参考格式与知识追踪能力
- 更丰富的项目级活动流与审阅视图
- 更复杂的 AI 长任务编排与上下文管理能力
- 更细的项目知识结构模板

### 12.3 长期演进方向

长期来看，Jixia 应沿着以下方向演进：

#### 方向一：更强的研究连续性

让用户从 Search 到 Project Docs 的整个过程拥有更少的上下文丢失和更稳定的知识回路。

#### 方向二：更强的引用与可追溯性

强化引用、证据来源、参考关系与文档间知识关联，但仍然避免把产品设计成显式跨模块投递流水线。

#### 方向三：更成熟的项目知识治理

围绕 Project Docs 发展更完整的项目知识组织能力，让项目真正成为团队知识资产的中心。

#### 方向四：更好的 AI 辅助，但不改变产品哲学

AI 可以越来越强，但产品哲学不变：**AI 帮助研究者做判断，不替代研究者做判断。**

### 12.4 明确不演进的方向

即便未来能力扩展，Jixia 也不应偏离以下边界：

- 不演进成完整 ELN / LIMS
- 不演进成实验执行管理系统
- 不演进成独立聊天产品
- 不演进成以自动流水线替代研究判断的系统

---

## 13. 一句话总结 Jixia 的产品定位

**Jixia 是一个面向科研实验室团队的研究操作系统：它以个人研究闭环为起点、以 Project 为正式协作单元、以 Project Docs 为共享知识中心、以 AI 作为嵌入式协作助手，持续支持研究判断的形成、沉淀与协作，而不是用流水线替代科研思考。**
